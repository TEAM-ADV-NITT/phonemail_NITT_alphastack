TEAM ADV — PhoneMail
Project Explanation & Development Guide

1. PROJECT OVERVIEW

PhoneMail is an email platform where a user's phone number acts as their email identity.

Example:
9876543210@phonemail.com

The goal is to make email communication easier for users who are more familiar with phone numbers than conventional email addresses.

TEAM ADV will build a web-based PhoneMail application with:
- A mobile-first interface
- A desktop web interface
- Phone-number-based registration and OTP verification
- Email conversations and threading
- Traditional email interoperability
- SMS notifications
- A backend API
- PostgreSQL database
- SMTP integration
- Dockerized deployment

The hackathon specification explicitly prioritizes the mobile client and requires the complete application to be containerized so that it can run using Docker Compose.

2. WHAT THE HACKATHON REQUIRES

The official specification requires an email application where phone numbers function as email IDs, for example:

9876543210@phonemail.com

Account access should support:
- Toll-free number and IVR-based account creation
- SMS-based interaction
- Web registration using Phone Number + OTP
- Password fallback if OTP is unavailable

Once an account exists, the user should be able to receive emails and access the service through mobile or web.

For users without the mobile application, the system should provide an SMS notification when an email is received.

The web client should provide a desktop email experience, while the mobile experience should follow a conversation/chat-oriented design.

3. HOW PHONEMAIL WORKS

A PhoneMail user is identified primarily by their phone number.

Example:

User phone number:
9876543210

PhoneMail address:
9876543210@phonemail.com

Basic communication flow:

User
  |
  v
9876543210
  |
  v
9876543210@phonemail.com
  |
  v
PhoneMail
  |
  +--> Inbox
  +--> Conversations
  +--> Sent
  +--> Drafts

The system should support communication between:
- PhoneMail users
- PhoneMail and conventional email users
- External email services such as Gmail

4. ACCOUNT CREATION AND AUTHENTICATION

WEB REGISTRATION

The primary web registration flow is:

1. User enters phone number.
2. System sends OTP.
3. User enters OTP.
4. Phone number is verified.
5. PhoneMail account is created.

If OTP is unavailable, the specification permits a password fallback.

IVR

IVR means Interactive Voice Response.

The proposed IVR flow is:

1. User calls the toll-free number.
2. Automated system answers.
3. User selects the required option, such as pressing 1.
4. The system starts the account-creation process.

SMS

SMS can be used for notifications and, where applicable, account interaction.

For users without the mobile app, an email notification can be delivered through SMS.

Example:

"You have received an email from <Sender>.
Subject: <Subject>."

11. GIT / GITHUB WORKFLOW

The project is hosted under the TEAM-ADV GitHub organization.

Recommended workflow:

1. Pull the latest main branch.
2. Create a feature branch.
3. Work only on the assigned feature.
4. Commit changes with a clear message.
5. Push the branch.
6. Open a Pull Request.
7. Review and merge into main.

Example branch names:

feature/auth
feature/inbox
feature/email-service
feature/sms
feature/ivr
feature/frontend-mobile
feature/frontend-desktop

Never commit:
- .env files
- API keys
- passwords
- private credentials
- node_modules

14. FINAL DEMO FLOW

The final demonstration should tell a simple story:

1. User opens PhoneMail.
2. User registers using their phone number.
3. OTP verifies the account.
4. Phone number becomes the user's PhoneMail identity.
5. User enters the inbox.
6. User receives an email.
7. Email appears as a conversation.
8. User opens and replies.
9. User composes a new email.
10. External email communication is demonstrated.
11. SMS notification is demonstrated where applicable.
12. Desktop and mobile responsive interfaces are shown.
13. The complete application is run using Docker Compose.

15. PROJECT PRINCIPLE

TEAM ADV should build the project as one complete product rather than as disconnected features.

Every feature should answer three questions:

- Does it help the user communicate?
- Does it integrate correctly with the rest of PhoneMail?
- Can another team member understand and maintain it?

The objective is to finish with a working, documented, containerized PhoneMail system that the entire team understands.
